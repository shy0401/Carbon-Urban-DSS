`…` = `docker compose -p carbon-urban-dss -f compose.yaml -f compose.demo.yaml exec -T api`

**따로 확인 (내 DB는 그대로 두고 재현만 보기)**: 저장소를 다른 폴더에 한 번 더 받아 별도 Docker 프로젝트로 가져옵니다.

```powershell
git clone https://github.com/shy0401/Carbon-Urban-DSS.git D:\dss-verify; cd D:\dss-verify
$env:DSS_PROJECT='carbon-urban-dss-importtest'; $env:DSS_COMPOSE_OVERRIDE='compose.validation.yaml'; $env:DSS_API_PORT='8010'; $env:DSS_WEB_PORT='5190'
scripts\dss.cmd ImportBundle -BundlePath D:\share\carbon-dss-bundle-<시각>.zip     # 끝나면 사례 25개 비교 결과가 나옴
docker compose -p carbon-urban-dss-importtest -f compose.yaml -f compose.validation.yaml down   # 확인 뒤 정리(볼륨 이름이 importtest인지 꼭 확인)
```

`MergeBundle`로 내 DB에 더한 뒤에는 내 자료가 섞여 사례 값이 달라질 수 있습니다. 그때 `VerifyCases`의 "자료 지문 다름"은 정상이며, 어떤 표·연도가 다른지 비교표에 적습니다. `MergeBundle`은 건축HUB 연도의 "수집 완료" 표시(`data/ops/history-progress.json`)를 바꾸지 않습니다. 이 표시가 다르면 같은 행이어도 2025년이 "잠정값"이 되고 감축 역산이 "자료 없음"이 되므로, 기준 PC와의 비교는 위 "따로 확인"(묶음의 표시를 자동 복원)으로 합니다.

## 4. 예상값 만드는 법 (수집 전에)

| 지표 | 공식 | 참고 범위 (기준 PC, 2025) |
|---|---|---|
| 공동주택 원단위 | 단지 전력 ÷ 단지 연면적 | 24~30 kWh/m² (전주 송천1동 29.06, 강서 명지1동 27.54, 강동 천호3동 단지 24.22) |
| 건물 전체 원단위 | 건축HUB 전력 ÷ 대장 연면적 | 41~78 kWh/m² (전주 개발지 격자 41.1, 강서 상업 격자 49.07, 강동 천호3동 78.40) |
| 기준 전력 E_b | 원단위 × 연면적 (또는 세대수 × 세대당 전력) | — |
| 추가 부하 비율 r | (원단위 × 추가 연면적) ÷ E_b | 사례 대부분 0.02~0.07 |
| 지역 전체 효율 (목표 t) | 1 − (1 − t) ÷ (1 + r) | t = 20%면 **21~25%** (사례 21.0~24.6%) |
| 필요 감축 kWh | E_b × (t + r) | — |
| 필요 감축 t | E_b × (t + r) × 0.4330 ÷ 1,000 | — |
| 태양광 kW | E_b × (t + r) ÷ (일사량 × 0.80) | 발전량 1,150(서울)~1,294(부산) kWh/kW |
| 개발 전후 | 사용승인 세대가 늘면 전력 증가(+) | 송천1동 +28.1% 연면적 → +15.4 GWh/년(추정) |
| 탄소공간지도 비율 | 이 도구 ÷ 탄소공간지도 (같은 칸) | 중앙값 0.67~0.76 (전주), 10~90% 0.08~1.17 |

예상 근거(어떤 공식, 어떤 참고값)를 예상표의 "예상 근거" 열에 적습니다. 예상이 틀려도 괜찮습니다. **왜 다른지 찾는 것**이 목표입니다.
