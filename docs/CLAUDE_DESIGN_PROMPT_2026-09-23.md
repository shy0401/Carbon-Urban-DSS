# Claude에게 전달할 디자인 적용 프롬프트 (D안 「도시계획 도면」)

먼저 `DESIGN.md`를 저장소의 `docs/DESIGN.md`로 커밋한다. 그다음 아래 코드 블록 전체를 새 Claude Code 작업에 붙여 넣는다. 프로젝트 루트에서 실행하고, 키 원문은 넣지 않는다.

```
당신은 Carbon Urban DSS 프런트엔드의 디자인 적용 담당자다. 목표는 docs/DESIGN.md의 D안 「도시계획 도면」을 현재 React/Vite 화면 전체에 적용하는 것이다. 기능, API 호출, 계산, 데이터 의미는 바꾸지 않는다. 설명만 하고 멈추지 말고, 조사 → 적용 → 검증 → 커밋을 단계별로 끝까지 진행하라.

저장소: https://github.com/shy0401/Carbon-Urban-DSS
대상: frontend/ (nginx localhost:5173, API는 FastAPI localhost:8000)

먼저 다음을 읽어라:
1. docs/DESIGN.md (이번 작업의 기준. 특히 2.3 근거 유형, 2.4 램프, 4.2 표제란, 6 지도 규칙)
2. README.md, docs/CLAUDE_HANDOFF_2026-09-23.md, docs/ARCHITECTURE.md, docs/IMPLEMENTATION_UPDATE.md, docs/TESTING.md, docs/CARBON_METHOD.md
3. frontend/package.json, 진입점, 라우터, 전역 스타일, 공통 컴포넌트, useAnalysisScope, 지도·차트 컴포넌트, Vitest와 E2E 테스트

첫 단계(조사, 코드 변경 없음):
- git status/log, 현재 브랜치를 확인하라. 사용자의 .idea/vcs.xml 변경은 건드리지도 커밋하지도 마라.
- 스타일 방식(일반 CSS, CSS Modules, Tailwind, CSS-in-JS 중 무엇인지), 지도 라이브러리(MapLibre/Leaflet/기타)와 렌더러, 차트 라이브러리, 아이콘·폰트 로딩 방식을 확인하라.
- 화면·라우트 목록과 각 화면이 쓰는 컴포넌트를 표로 정리하라.
- 서버 응답에서 실측/공공데이터 계산/추정/시나리오/결측, 미학습/표본 부족 상태를 나타내는 필드가 무엇인지 찾아 목록으로 만들어라. 필드가 없는 곳은 표시하지 말고 백로그로 남긴다. 프런트에서 상태를 새로 추론하지 마라.
- E2E와 Vitest가 의존하는 셀렉터(data-testid, role, 표시 문구)를 목록화하라.
- 컴포넌트 안에 하드코딩된 색·폰트를 rg로 집계하라.
- 기존 E2E 또는 Playwright로 주요 화면의 변경 전 캡처를 1440px, 390px, 인쇄 미리보기로 data/validation/design/before/에 저장하라.
- 위 결과와 적용 계획을 docs/DESIGN_APPLY_LOG.md에 짧게 기록하고, 사용자 확인을 기다리지 말고 다음 단계로 진행하라.

적용 순서(단계마다 테스트 후 커밋):
1. 토큰과 서체: frontend/src/styles/tokens.css, frontend/src/theme/palette.ts를 DESIGN.md 값 그대로 만들고 진입점에서 import한다. Pretendard Variable은 CDN이 아니라 로컬 번들(npm 패키지 또는 public/fonts)로 넣는다(오프라인 시연 모드 때문). 전역 바탕·먹·숫자 tabular-nums·keep-all을 적용한다. palette.ts와 tokens.css 키 일치 Vitest를 추가한다.
2. 앱 셸: 먹녹색 사이드바, 상단 표제란(분석연도, 격자, 선택 격자 수, 자료 기준일, 온라인/오프라인). 표제란은 useAnalysisScope 값을 읽기만 하고 범위 변경 로직은 기존 컨트롤을 그대로 쓴다. 모바일은 한 줄 요약으로 접는다.
3. 근거 체계: ProvenanceBadge, MissingValue 공통 컴포넌트를 만들고, 첫 단계에서 찾은 상태 필드가 있는 모든 곳에 적용한다. 결측을 0이나 빈칸으로 보이게 하는 기존 표시가 있으면 고치고 로그에 남긴다. "데이터 미확보" 안내를 미관 때문에 숨기거나 줄이지 마라.
4. 지도: 부하/편익 램프, 결측 해치 패턴(사용 중인 라이브러리 방식으로), 선택 격자 외곽선+헤일로, 범례의 "자료 미확보" 칩 분리, 용도지역 외곽선 오버레이 토큰(자료가 없으면 켰을 때 미확보 안내), 오프라인·타일 장애 시 도면지 바탕+1km 참조 격자, 축척 막대. 기존의 실제 값 기반 범례 경계 계산은 그대로 둔다.
5. 대시보드와 나머지 화면: 지표 8개 카드, 월별 기상 차트(결측 월은 선을 끊고 해치 띠), 수집 데이터 화면, 모델 검증 화면(미학습·표본 부족·데이터 미확보 문구 구분 유지), 계획안 시뮬레이션(5·10·20·30·40층, 개념 배치도), 계획안 비교 3색.
6. 검토 보고서와 인쇄: /reports 화면, A4 인쇄 CSS, 첫 장 표제란+근거 해시, 해치·점선 인쇄 유지, 표·차트 페이지 분할 방지.
7. 정리: 하드코딩 색 재집계(tokens.css, palette.ts 외 0개 목표, 남는 것은 사유 기록), 미사용 스타일 제거.

필수 작업 방식:
- 변경 전 관련 컴포넌트와 테스트를 읽고, 바꿀 화면을 실행해 확인한 뒤 수정하라.
- 백엔드, API 계약, 계산 로직, 라우트, 수치 형식의 의미를 바꾸지 마라. 표시 문구를 바꿔야 하면 의미가 같은지 확인하고, 테스트가 그 문구에 의존하면 테스트를 함께 고치고 로그에 사유를 남겨라. data-testid와 role은 유지하라.
- UI 킷을 통째로 도입하지 마라. 새 의존성이 꼭 필요하면 이유와 번들 크기 변화를 기록하라. 초기 JS 번들(현재 약 2.52MB, 압축 약 774KB)을 늘리지 마라.
- 기존 모바일 조건을 지켜라: 390px에서 문서 가로 넘침 0, 넓은 표는 표 영역 안에서만 스크롤.
- 접근성: 본문 대비 4.5:1, 모든 인터랙티브 요소 포커스 링, 색만으로 의미 전달 금지, prefers-reduced-motion 존중.
- docker compose down -v, 파괴적 Git 명령, 강제 푸시를 하지 마라. .env, .secrets, 캐시, 백업, 개인 설정 파일을 커밋하지 마라.
- 의미 있는 단계마다 커밋하고 원격에 푸시하라. 커밋 메시지는 "design(D): <단계>" 형식.

검증(가능한 환경에서 모두 실행, 못 한 것은 이유 기록):
- cd frontend && npm ci && npm test && npm run build
- 기존 E2E 전체와 보완 E2E 전체
- 1440px, 390px, 인쇄 미리보기 변경 후 캡처를 data/validation/design/after/에 저장하고 before와 같은 화면·같은 상태로 맞춘다.
- 오프라인 모드(DEMO_OFFLINE_MODE 또는 웹 버튼)에서 지도·폰트·아이콘이 깨지지 않는지 확인한다.
- 빌드 산출물의 초기 JS 크기를 변경 전과 비교한다.
- 주요 텍스트·배지·범례 대비를 점검한다.

문서 갱신:
- docs/DESIGN_APPLY_LOG.md에 단계별 변경 파일, 결정, 예외, 남은 하드코딩, 백로그를 기록하라.
- 적용 중 DESIGN.md와 실제 데이터 의미가 충돌하면 데이터 의미를 따르고 DESIGN.md를 고친 뒤 사유를 남겨라.
- README.md 구현 안내에 docs/DESIGN.md 링크를 추가하고, docs/CLAUDE_HANDOFF_2026-09-23.md에 디자인 적용 결과를 한 단락으로 덧붙여라.

최종 보고는 다음 순서로 작성하라: ① 바뀐 화면과 핵심 파일 ② 근거 유형·결측 표시가 적용된 위치와 서버 필드 매핑 ③ 테스트·빌드·E2E 결과와 번들 크기 비교 ④ 전후 캡처 경로 ⑤ 적용하지 못한 부분과 이유, 다음 작업. 파일 링크와 커밋 ID를 포함하고, 하지 않은 것을 했다고 쓰지 마라.
```
